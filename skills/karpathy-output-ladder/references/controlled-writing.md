# 1 级：受控文字

## ASD-STE100 是什么

ASD-STE100（Simplified Technical English，简化技术英语）是欧洲航空航天与防务工业协会（ASD）1986 年起维护的受控英语标准。起因是航空公司的维修手册要给各国技师看，读错一条指令可能出人命。当前版本是 Issue 9（2025 年 1 月），9 节 53 条写作规则，外加约 900 个受控词（每个词只有一个意思、一种词性）。

它消掉两类歧义：一个词有多个意思，一句话有多种结构。

Karpathy 说模型很熟悉这套规范，用它解释东西通常更好读；但规范太严，他有时只要求"做到 80%"。

标准可以免费申请下载，但正文和词表**不可再分发**。本 skill 只用规则类别，不含词表，所以：
- **结构规则**（句子长什么样）可以照做，linter 也能查。
- **词汇规则**（该用哪个词）只能当方向：用最普通的词，同一个东西始终用一个词。

## 结构规则

| 规则 | 这样写 | 不要这样写 |
|---|---|---|
| 主动语态 | 脚本删除临时文件。/ The script deletes the temp file. | 临时文件被脚本删除。/ The temp file is deleted. |
| 一句一个动作 | 打开文件。读第 3 行。 | 打开文件并读第 3 行，然后检查是否匹配。 |
| 句长 | 见下面的分档表 | 一句套三层从句 |
| 不用分号 | 拆成两句 | 先开票；再发货 |
| 名词堆叠 ≤3 层 | 连接池的超时值 | 高压燃油泵进口阀门总成 |
| 不为省字删成分 | 未备份的文件会丢失。 | 文件未备份将丢失。（哪些文件？） |
| 条件在前 | 如果构建失败，读日志。 | 读日志，如果构建失败的话。 |
| 保留情态 | "请求可能已失败"照写 | 改成"请求失败" |
| 段落 | 一段一个主题，≤6 句 | 一段塞三件事 |
| 列表 | 3 步以上、3 个条件以上用编号列表 | 把步骤塞进一句 |
| 英文：不用短语动词 | Start the job. / Remove the panel. | Spin up the job. / Take off the panel. |
| 英文：简单时态 | We received the report. | We have received the report. |

英文现在完成时的例外：当"现在仍然成立"本身是信息时（The job has finished, and the output is ready），保留它。中文同理："任务已完成，结果可以直接读"里的"已"不要删。

## 词汇规则（方向）

| 规则 | 这样写 | 不要这样写 |
|---|---|---|
| 一词一义 | 全文都用"检查" | 检查、校验、核对、确认轮着用 |
| 动词优先 | 分析日志。/ Analyze the log. | 对日志进行分析。/ Perform an analysis of the log. |
| 删营销词 | 删掉，或换成测量值 | 无缝、强大、赋能、闭环、极致、一站式、seamless、robust、powerful、cutting-edge |
| 术语首次定义 | 幂等（执行两次结果一样） | 直接用黑话，后面全靠猜 |
| 具体化 | 3 秒内重试 2 次 | 快速重试若干次 |

## 中文特有的坑

英文规则逐条翻译过来治不了中文的毛病。中文要额外查这六类：

1. **虚动词**：进行、加以、作出、予以、开展 + 动作名词。"对配置进行修改" → "修改配置"。
2. **套话**：需要注意的是、值得一提的是、在一定程度上、某种意义上、综上所述、不难看出。删掉信息量不变。
3. **营销词**：无缝、强大、赋能、闭环、极致、丝滑、一站式、颠覆、领先。
4. **同义轮换**：用户/客户/使用者，检查/校验/核对。读者分不清是一个东西还是几个。
5. **含糊限定**：若干、一些、相关、适当、酌情。要么给数量和范围，要么删。（"必要时"如果是真实的条件，保留。）
6. **翻译腔**：基于……的情况下、对于……而言、这是一个……的事实。去掉外壳，主语和动作就清楚了。

## 严格度分档

| 严格度 | 英文句长 | 中文句长 | 执行什么 |
|---|---|---|---|
| 90～100 | 操作 ≤20 词，说明 ≤25 词 | 操作 ≤25 字，说明 ≤40 字 | 全部结构规则 + 一词一义 + 主动语态 |
| 70～89（默认 80） | 操作 ≤20 词，说明 ≤25 词 | 操作 ≤25 字，说明 ≤40 字 | 结构规则；不用分号、虚动词、营销词；用词可以有变化，被动语态只提醒 |
| 40～69 | ≤30 词 | ≤50 字 | 短句、不用分号、不用营销词，其余是建议 |
| <40 | — | — | 只给"说人话"的建议 |

用户说法 → 严格度：
- "严格 STE""完整 ASD-STE100" → 100
- "80%""STE 风格""用 STE"（没给数字）或什么都没说 → 80
- "简单点""说人话" → 50
- 给了数字 → 用那个数字

中文 linter 默认按说明句 40 字检查；检查操作步骤时加 `--max-chars 25`。

## 改写前扫一遍

改写前先扫一遍，每一项都能指出具体的字词或标点：

1. 同一个东西有没有好几个名字？
2. 有没有情态词叠在一起，最后什么都没断言？（"可能在一定程度上有助于"）
3. 有没有虚动词？
4. 有没有营销词？
5. 有没有用分号、破折号、"并且/同时/从而"把几件事串成一句？
6. 中文：有没有套话、翻译腔、含糊限定？英文：有没有短语动词（spin up、reach out、dive into）？

## 情态是内容

最常见的翻车：为了满足句长上限，把"可能"删了。

- "请求可能已失败"改成"请求失败"，结论变了。
- "可能是 X 导致的"改成"X 是原因"，结论变了。
- 三个"可能"分别修饰三件不同的事，就保留三个，各放一句。

句子太长就拆，不要删情态。两个 linter 都不会标记情态词，这是有意的。

## 例子：同一段话的三档

**原文：**

> 本次版本对垃圾回收器进行了重新设计，现已采用并发标记机制；因此，停顿时间——此前一直是对延迟敏感的服务的一大痛点——可能会得到显著缩短，不过在高分配压力下吞吐量可能会略有下降。

**100：**

> 本版本修改了垃圾回收器。回收器现在在程序运行的同时标记对象。这可能使停顿时间明显缩短。对延迟敏感的服务受停顿影响最大。程序分配大量内存时，吞吐量可能少量下降。

**80：**

> 本版本重新设计了垃圾回收器，标记阶段现在和程序并发执行，停顿时间可能明显缩短。延迟敏感的服务以前最受停顿困扰。代价是：内存分配压力大时，吞吐量可能略有下降。

**50：**

> 这个版本重写了垃圾回收器，改成并发标记，停顿时间可能会短很多，对延迟敏感的服务是好消息。不过分配压力大的时候，吞吐量可能会掉一点。

三档都保留了两个"可能"。都没有写停顿缩短了多少，因为原文没说。

## 例子：英文

**原文：**

> It is important to note that the deployment pipeline has been significantly enhanced to seamlessly leverage parallel execution; consequently, build times may potentially be reduced.

**80：**

> The deployment pipeline now runs jobs in parallel. This change can make builds faster.

改了什么：删掉套话 "It is important to note"；删掉营销词 "seamlessly""significantly enhanced"；"leverage" 换成 "runs"；分号拆成两句；"may potentially" 两层情态合成一个 "can"，保留了不确定性；原文没给数字，改写也不给。

## 例子：解释一段日志（中文，80）

**原文（模型输出）：**

> 经过对相关日志的深入分析，我们发现该问题在一定程度上可能与连接池配置存在一定关联；值得注意的是，在高并发场景下，相关连接可能会出现被耗尽的情况，从而进一步导致请求超时现象的发生。

**改写：**

> 请求超时的原因可能是连接池耗尽。日志显示，高并发时连接池的连接可能全部占满。新请求拿不到连接，就会超时。下一步：检查连接池的最大连接数。

改了什么：删掉"经过深入分析""值得注意的是""在一定程度上""一定关联"等套话；分号拆开；"从而进一步导致……现象的发生"改成直接的因果句；保留两处"可能"。

## 和其他场景的分工

- **解释给人看**（本 skill 的主要用途）：可以重组结构、加例子、加术语定义。
- **改写给 agent 读的字符串**（工具描述、报错、prompt）：只改形式，不加不减信息，默认只输出改写结果。
- **营销、文学**：不适用，会抹掉语气。
